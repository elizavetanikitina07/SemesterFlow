# Требования к веб-приложению SemesterFlow

**Тема курсовой работы** — «Разработка веб-приложения для планирования учебного семестра».

## 1. Назначение приложения

SemesterFlow — личный учебный планировщик. В нём студент ведёт список дисциплин и заданий, отмечает выполненные работы, записывает полученные оценки и проверяет, какие задания нужно сдать в ближайшее время.

## 2. Цель и задачи разработки

Цель проекта — разработать веб-приложение, позволяющее студентам организовывать учебный процесс, управлять дисциплинами и заданиями, отслеживать сроки выполнения и успеваемость.

Задачи разработки:

- Создать учётные записи и обеспечить доступ к личной панели после входа.
- Организовать хранение дисциплин и связанных с ними заданий.
- Реализовать поиск, фильтрацию и отображение ближайших дедлайнов.
- Дать студенту возможность отмечать выполнение заданий и записывать оценки.
- Проверять ввод, обрабатывать ошибки и обеспечивать изоляцию данных пользователей.

## 3. Целевая аудитория

Основные пользователи — студенты, которые самостоятельно планируют учебный семестр и ведут задания по нескольким дисциплинам. Для работы с приложением достаточно навыков использования браузера и заполнения веб-форм.

## 4. Функциональные требования

| Функция | Требование |
| --- | --- |
| Регистрация и вход | Пользователь может создать учётную запись и войти с её помощью. Если данные введены неверно, приложение показывает понятное сообщение. |
| Личная панель | После входа пользователь видит ближайшие дедлайны по своим невыполненным заданиям в порядке возрастания срока и может перейти к спискам дисциплин и заданий. Если ближайших дедлайнов нет, панель сообщает об этом. |
| Дисциплины | Пользователь может создать дисциплину, просмотреть её и список своих дисциплин, изменить название и удалить дисциплину. Операция удаления должна сохранять целостность связанных данных. |
| Задания | Пользователь может создать задание в своей дисциплине, просмотреть его и список своих заданий, изменить данные и удалить задание. Для задания указываются название, дисциплина, дедлайн и статус выполнения. Оценку можно добавить позже. |
| Поиск и фильтрация | Поиск находит задания по полному названию или его части. Фильтры позволяют отбирать задания по дисциплине, диапазону дат дедлайна и статусу. Поиск и фильтры можно применять одновременно и сбрасывать. |
| Выполнение и оценки | Пользователь может отметить задание выполненным, записать или исправить полученную оценку. Статус и оценка отображаются при просмотре задания. Отсутствие оценки должно быть различимо. |
| Валидация и ошибки | Клиент и сервер проверяют обязательные поля и допустимость значений, в том числе корректность даты, статуса и границ диапазона фильтра. При ошибке приложение сообщает, что нужно исправить. Некорректные данные не сохраняются. |
| Навигация | Клиентская часть содержит не менее трёх маршрутов. Личная панель, дисциплины и задания доступны после входа. |

Календарь заданий и расширенная статистика успеваемости относятся к дополнительной функциональности.

## 5. Нефункциональные требования

- **Удобство использования.** Поля форм имеют понятные подписи. Интерфейс различает загрузку, пустой список и ошибку, чтобы пользователь понимал, что происходит.
- **Адаптивность.** Основные формы, списки и навигация доступны в браузере на компьютере и смартфоне.
- **Надёжность.** Успешно сохранённые изменения доступны после обновления страницы и повторного входа. При сбое приложение сообщает об ошибке операции.
- **Сопровождаемость.** Клиентская и серверная части используют стек из `AGENTS.md`. Изменения схемы MySQL оформляются миграциями Prisma.

## 6. Основные пользовательские сценарии

1. **Начать работу.** Студент регистрируется, входит в свою учётную запись и открывает личную панель.
2. **Запланировать работу.** Студент создаёт дисциплину, добавляет к ней задание с дедлайном и видит его в списке заданий.
3. **Найти задание.** Студент вводит часть названия, выбирает дисциплину, диапазон дедлайнов и статус, затем открывает нужный результат.
4. **Проверить сроки и успеваемость.** Студент просматривает ближайшие дедлайны на панели, отмечает сданное задание выполненным и позже записывает полученную оценку.
5. **Исправить ввод.** Студент отправляет форму с пропущенным обязательным полем, получает сообщение, дополняет форму и сохраняет запись.

## 7. Требования к безопасности

- Пароли пользователей хранятся в базе данных в виде хешей bcrypt. Пароли и их хеши не включаются в ответы сервера.
- Для защищённых запросов клиент передаёт JWT в заголовке `Authorization: Bearer <token>`. Сервер проверяет подпись и срок действия токена.
- Сервер проверяет принадлежность дисциплин и заданий текущему пользователю при просмотре, создании связанных записей, изменении и удалении. Панель, списки и поиск возвращают только данные текущего пользователя.
- Сервер отклоняет запросы к защищённым данным без действительного токена и запрещает доступ к чужим записям даже при передаче их идентификаторов напрямую.
- Секреты передаются через переменные окружения. Пароли и секретные ключи не хранятся в репозитории.

## 8. Критерии готовности приложения

- Схему базы данных можно развернуть миграциями Prisma. Клиентская часть содержит не менее трёх маршрутов.
- Новый пользователь может зарегистрироваться, войти и открыть личную панель. При неверных данных для входа приложение показывает ошибку.
- Пользователь может создать, просмотреть, изменить и удалить свои дисциплины и задания. Сохранённые изменения видны после обновления страницы.
- На контрольном наборе заданий поиск по части названия, каждый фильтр и их совместное применение возвращают ожидаемые записи. Сброс возвращает полный список заданий пользователя.
- Личная панель показывает ближайшие дедлайны по невыполненным заданиям в порядке возрастания срока. Пользователь может изменить статус и сохранить оценку.
- Форма с обязательным пустым полем или некорректной датой показывает ошибку. Прямой запрос с такими данными также отклоняется сервером.
- Проверка с двумя учётными записями подтверждает, что пользователь не может просматривать, изменять или удалять данные другого пользователя, в том числе при обращении напрямую к серверу. Запросы без действительного токена отклоняются.

Критерии готовности относятся к основной функциональности. Календарь и расширенная статистика могут быть реализованы отдельно.
